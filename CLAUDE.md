# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`wpflow` ports [xyflow](https://github.com/xyflow/xyflow) (React Flow) to WPF: an interactive node/edge graph editor. Planning documents live in `work-doc/` (`ROADMAP.md` for what is left and the target demo, `ECART-XYFLOW.md` for the gap with xyflow, `ARCHITECTURE-DECISIONS.md` for decisions/open questions). Put new roadmap/planning markdown files there and check them before making architectural changes.

The `demo` must keep resembling the homepage demo of https://reactflow.dev/ (dotted background, white rounded cards with real WPF controls, dashed animated bezier edges, minimap, controls). A reference screenshot is in `work-doc/screenshots/demo.png`.

User documentation lives in `doc/` (Learn / API Reference / Examples, in French, mirroring reactflow.dev); keep it in sync when changing the public API. Link check: every relative link in `doc/**/*.md` must resolve.

Solution `wpflow.sln`, Windows only:

- `src/Wpflow.Core` (net8.0, **no WPF dependency**) — logic ported from `@xyflow/system`: immutable model (`Node`, `Edge`, `HandleInfo`), viewport math, edge path generation (SVG path strings), bounds/handle helpers, and `Changes.Apply` (NodeChange/EdgeChange). New logic goes here first, with tests.
- `src/Wpflow.Wpf` (net8.0-windows) — WPF controls over the core: `FlowView`, `NodeHost`, `Handle`, `EdgeLayer`, `FlowBackground`, `MiniMap`, `FlowControls`; default styles in `Themes/Generic.xaml`.
- `src/Wpflow.Blazor` (net8.0, branche `blazor`) — version Blazor au-dessus du noyau (Server et WebAssembly) : `FlowView` (classe partielle : `.razor`, `.razor.cs`, `.Options`, `.Gestures`, `.Editing`, `.Api`), `FlowLayer` / `FlowNodeHost` (rendu mémorisé), `FlowHandle`, `NodeResizer`/`NodeResizeControl`/`NodeRotator`, toolbars, `FlowControls`, `FlowMiniMap`, `FlowPanel`, pont JS `wwwroot/wpflow.js` ; démo `demo/blazor-shared/` (composant) hébergée par `demo/blazor/` (Server, lancer en `Development`) et `demo/blazor-wasm/` ; tests bUnit `tests/Wpflow.Blazor.Tests`, tests de bout en bout dans un vrai Chrome `tests/Wpflow.Blazor.E2E` (Playwright, Chrome installé) ; doc `doc/blazor.md`, état dans `work-doc/BLAZOR.md`.
- `demo/wpf/` (net10.0-windows, because only the .NET 10 runtime is installed locally) — homepage-style WPF demo. All demos live under `demo/` (`wpf`, `blazor`, `blazor-shared`, `blazor-wasm`).
- `tests/Wpflow.Core.Tests` (xUnit, net10.0) — tests for the core only.
- `tests/Wpflow.Wpf.Tests` (xUnit, net10.0-windows, STA thread helper `Sta.Run`) — MVVM adapter and bindable selection of `FlowView` (needs `InternalsVisibleTo`).

## Commands

```bash
dotnet build wpflow.sln
dotnet run --project demo/wpf
dotnet test tests/Wpflow.Core.Tests
dotnet test tests/Wpflow.Wpf.Tests
dotnet test tests/Wpflow.Core.Tests --filter "FullyQualifiedName~EdgePathsTests"   # one test class
```

Headless visual check of the demo (captures the window to a PNG and exits); `WPFLOW_SELFTEST=1` additionally drives the real mouse (drag, connect, reconnect an edge, wheel zoom, pan, select, undo/redo) and writes a `.log` next to the PNG; `WPFLOW_PERF=N` instead runs the perf spike on N generated nodes (add `WPFLOW_PERF_VIRT=1` for virtualisation) and writes `.perf.log`. `WPFLOW_EXAMPLES=selftest` opens the examples window and runs 60 checks (customization and MVVM tabs, groups, keyboard, toolbar, palette drag&drop, loose mode, validator, translateExtent, JSON, dark theme, virtualisation), logging `OK`/`ECHEC` lines to the `.log` and saving per-tab PNGs. These tests use real Win32 mouse/keyboard input, so the window must be allowed to take the foreground and nothing else should touch the mouse while they run. Do not overwrite `work-doc/screenshots/demo.png` with a self-test run (it is the reference for the untouched demo):

```bash
WPFLOW_SCREENSHOT="D:/git/wpflow/work-doc/screenshots/out.png" WPFLOW_SELFTEST=1 dotnet run --project demo/wpf --no-build
```

All real-mouse WPF self-tests at once, with a failing exit code on any `ECHEC` line, exception or timeout (also run in CI and before publishing): `powershell -File tests/run-wpf-selftests.ps1`. On a developer machine, run them hidden with `pwsh -File tests/run-wpf-selftests-sandbox.ps1 [-Only matrix]` instead: same runs inside Windows Sandbox (its own mouse and keyboard, window placed off screen, no network), logs in `artifacts/selftest`; it refuses to start while another sandbox is running. Do not run the direct script on someone's desktop without asking. Packages consumed like a user would (fresh `dotnet new` apps outside the solution, README quickstart code): `powershell -File tests/consumers/run.ps1 [-Only wpf|blazor]`. Without Chrome, set `WPFLOW_BROWSER_CHANNEL=msedge`; without the .NET 8 runtime, run Blazor tests with `DOTNET_ROLL_FORWARD=Major WPFLOW_SERVER_DEMO_TFM=net10.0`. The schema-editor test app (ROADMAP-TESTS lot 2) is `tests/Scenarios.Shared` + `tests/Scenarios.Blazor{,.Server,.Wasm}`, driven by `ScenarioTests` in the E2E project (test classes run one at a time), and `tests/Scenarios.Wpf` (real mouse, `Runner.cs`, every scenario in controlled mode then in MVVM (`WPFLOW_MVVM=1` opens the app that way), part of `run-wpf-selftests.ps1`; pass `-Only scenarios`, a single name since `-File` does not split lists). Events and gestures are specified once in `tests/Scenarios.Shared/GestureMatrix.cs` (gesture → exact event sequence, the parity table) and `EventCatalog.cs` (every public event, enforced by `EventMatrixGuardTests`); both views replay it with real input: WPF `MatrixRunner.cs` (`-Only matrix`, `WPFLOW_GESTURE=prefixes`), Blazor `MatrixTests.cs` (Server and WebAssembly). A new event or interaction needs its gesture there. Public API changes go in `CHANGELOG.md`; `dotnet pack` validates the API against `PackageValidationBaselineVersion` (intended breaks: `CompatibilitySuppressions.xml`).

## Architecture (WPF layer)

- **State flows through changes, like React Flow.** `FlowView.Nodes` / `Edges` are immutable record lists. UI interactions never mutate them: they build `NodeChange`/`EdgeChange` lists, raise `NodeChangesRequested`/`EdgeChangesRequested`, and — if `AutoApplyChanges` (default true) — apply them via `Changes.Apply`. Set `AutoApplyChanges=false` for a controlled mode.
- **Layers inside `PART_Viewport`** (a `Grid` whose `RenderTransform` is the `Viewport` matrix): `EdgeLayer` (one self-drawing `EdgeVisual` per edge (path, wide transparent hit stroke, arrows, animated dashes all in `OnRender`) plus lazily created `EdgeLabel`s) → `Canvas` of `NodeHost`s → connection-preview path. `FlowBackground` sits outside the transform and uses a tiled `DrawingBrush` whose transform follows the viewport. The control's `Content` is an overlay (hero text, `MiniMap`, `FlowControls`).
- **All mouse interaction is centralised in `FlowView`** (`OnMouseLeftButtonDown/Move/Up`, modes Pan/DragNodes/Connect/Select), found by walking up from `e.OriginalSource` to `NodeHost`/`Handle`/`EdgeVisual`. Child controls (Slider, TextBox…) that mark events handled therefore keep working inside nodes.
- **Node content:** `NodeHost` looks up a `DataTemplate` with key `wpflow-node-{Node.Type}` (DataContext = the `Node`; put view-model state in `Node.Data`); otherwise it builds the React Flow-style default node (`input`/`output`/`default` handle layout).
- **Resizing:** `Node.FixedWidth/FixedHeight` set the explicit size applied to `NodeHost`; `NodeResizer` (place it inside the node template after the card but before the `Handle`s, with stretching content) emits `NodeResizeChange`. Selected custom-template nodes get an outline from the `NodeHost` style.
- **Measurement loop:** `NodeHost` measures its size and its `Handle` children (relative bounds) after layout (`RequestMeasure`, coalesced at `DispatcherPriority.Loaded`) and reports to `FlowView.OnNodeMeasured`, which emits a `NodeDimensionsChange` and stores handle info used for edge endpoints and connection hit-testing. Edges are not drawn until their endpoints are measured.
- **Nested nodes:** `Node.Position` is relative to `ParentId`. `FlowView._nodeIndex` holds nodes in **absolute** coordinates (with `ParentId` cleared) and is what edges, handles, connections, minimap (`AbsoluteNodes`) and the selection box use; `_rawIndex` holds nodes as supplied and is used for drag constraints (`ConstrainPosition`: `ExtentParent`, then `NodeExtent`). Z-index = depth. `NodeHost` skips work only if the node reference *and* its absolute position are unchanged.
- **Virtualisation:** with `OnlyRenderVisibleElements`, `NodeHost`s and `EdgeVisual`s are *created lazily* (`SyncHost`, `EdgeLayer.Refresh` with show/keep rects): shown within 300 px of the view, kept hidden up to 900 px, absent beyond (so memory no longer scales with node count). Selected nodes are always shown. `_handleMap` keeps measured handle info for absent nodes so edges still resolve. Offscreen never-measured nodes are never created, so bounds/fitView/minimap only know measured nodes.
- **Customisation by resources:** everything replaceable is looked up with `TryFindResource` once per `EdgeLayer.Refresh` (`Resolver`) — `wpflow-node-{type}` (DataTemplate, also for built-in types), `wpflow-edge-{type}` (`IEdgePathProvider`, overrides even built-ins), `wpflow-edge-template-{type}` (DataTemplate with an `EdgeRenderContext`; such edges use `EdgeTemplateVisual` instead of the self-drawing `EdgeVisual`), `wpflow-edge-label-{type}`, `wpflow-marker-{key}` (Geometry, pointing +x at the origin; `Edge.MarkerEndKey/MarkerStartKey`). `Handle` has no template by default (draws itself) but honours a `Template` and `Width/Height` from a Style. `IEdgePathProvider`/`EdgePathProviders.ForType` live in Core. The WPF unit tests host a single STA thread with an `Application` (`Sta.Run`) and must assign the default style explicitly.
- **Themes:** `ColorMode` merges `Themes/Light.xaml` or `Dark.xaml` into `FlowView.Resources`; code that draws (edges, minimap, default nodes) must read colors via `FlowView.ThemeBrush("Flow.…")`, XAML uses `{DynamicResource Flow.…}`.
- **Input extras:** keyboard navigation and Space+drag/middle-button pan live in `FlowView`; touch pinch uses `ManipulationDelta` (untested on hardware); `DropRequested` serves palette drag&drop; `EdgeLabelTemplate`, `NodeToolbar`, `FlowPanel` complete the component set.
- **MVVM (shared, `Wpflow.Core/Mvvm/`, both views):** `FlowView.NodesSource`/`EdgesSource` (+ `NodeMapping`/`EdgeMapping`, deriving from Core's `NodeMappingBase`/`EdgeMappingBase`; property names read by reflection, one table per property in `ModelBinding.cs` for read, write and history rebase) feed `SourceAdapter<T>`, which projects ViewModels to the immutable records (unchanged ones keep their reference) and, in `ApplyNodeChanges`/`ApplyEdgeChanges`, writes applied changes back to the ViewModels (position, size, selection, removal, factories for adds). `Writing` suppresses the echo of those writes. `SelectedNodes`/`SelectedEdges`/`SelectedNode` are kept in sync by `SelectionMirror` (an external `ObservableCollection` is edited in place, deferred if inside its own CollectionChanged). Commands (`Mvvm/FlowView.Commands.cs`): `Run(command, param)` checks `CanExecute`; `ConnectCommand`/`NodesDeleteCommand`/`EdgesDeleteCommand` replace the automatic action, the others notify; click detection uses `_pressedNode/_pressedEdge/_pressedPane` and a 4 px threshold in `OnMouseLeftButtonUp`. `Controller` (IFlowController wrapper, republished after a OneWayToSource binding nulls it) and `History` (IFlowHistory, replaces the built-in stacks) live there too; `Zoom` is synced both ways with `Viewport` (`SyncZoom`). `ToJson`/`LoadJson` go through `NodeSourceAdapter.Load` (factories required). Undo/Redo still work with a source: history holds record snapshots and `Restore` writes the diff back (`NodeSourceAdapter.Diff`); ViewModels removed by the view are kept so an undo re-adds the same object.
- **Parity between views is enforced:** `ViewParityTests` (in `Wpflow.Wpf.Tests`) fails when an event or setting exists on one side only; add it to both or list it there with the platform reason. `EventCommandTests` requires a command for every WPF event (`Mvvm/FlowView.EventCommands.cs`, subscribed only while the command is set). Same gestures must raise the same events in the same order on both sides (checked by the scenario apps' event journals).
- **`FlowView` partial files:** `FlowView.cs` (properties, sync with the model, measurement, selection, constraints), `FlowView.Input.cs` (mouse/keyboard/hover/wheel, click-connect, key options), `FlowView.Connect.cs` (connection line, candidate search, validation, reconnect, selection box, handle status), `FlowView.Interaction.cs` (global toggles, auto-pan, connect/double-click/context-menu events), `FlowView.Options.cs` (P2/P3 dependency properties, events and argument types), `FlowView.Api.cs` (animated viewport, `useReactFlow`-style instance API, delete, copy/paste, image export), `FlowView.Extras.cs` (background layers, portal layer), `Mvvm/*`. Gestures are computed in **flow** coordinates (`_mouseStartFlow`) so auto-pan keeps them correct. `Node.Origin`/`NodeOrigin` shift `_nodeIndex` positions (top-left) while `_rawIndex` (`_useRaw`) keeps stored positions; `ConstrainPosition` works on the top-left corner. Hidden nodes/edges are skipped by `GetEdgeEnds`, `AbsoluteNodes`, box selection, candidates and fit.
- **Shared interaction logic (`Wpflow.Core/Interaction/`):** both views (WPF, Blazor) call the same pure helpers instead of duplicating them — `ConnectionSearch`, `EdgeEndpoints`, `NodeConstraints`, `DragSelection`, `SelectionOps`, `GraphHistory`, `GraphDeletion`, `WheelInput`, `AutoPan`, `ViewFitting`, `Virtualization`, `MiniMapMath`, `NodeZOrder`/`EdgeZOrder`, `NodeRotation`, `KeyboardMove`, `EdgeMarkerMath`, plus the shared option enums and `FitViewOptions` (`FlowEnums.cs`). **New interaction logic goes there first, with tests in `Wpflow.Core.Tests/InteractionTests.cs`**; a view only keeps input handling, rendering and events. WPF behaviour (covered by the real-mouse self-tests) is the reference.
- **Shared but not public (`Wpflow.Core/Interaction/Shared/`):** logic both views need that must not enlarge the public API (`ViewLogic`: click tolerance, connection line path, pan-to-show, history rebase; `SelectionTracker`). The files hold `internal` types and are compiled into `Wpflow.Core` (tested there, `InternalsVisibleTo` Core.Tests only) and linked into `Wpflow.Wpf` and `Wpflow.Blazor`. Do not replace this with `InternalsVisibleTo` between packages (mixed package versions would break at run time).
- **Per-frame code (drag, pan, pulled wire) must not allocate per element:** both views reuse a node's absolute copy while the node and its position are unchanged (`_previousRaw` in WPF `OnNodesChanged`, Blazor `RebuildIndex`); Blazor caches node styles/classes and edge paths.
- **Core extras:** `GraphSerializer` (React Flow JSON shape), `GraphLayout`, `NodeTree`, `Connections` (strict/loose), `ViewportMath.ClampToExtent` (translateExtent). `EdgePaths` was compared with the real `@xyflow/system` sources (smoothstep ported from the recent version); re-fetch `packages/system/src/utils/edges/*.ts` from the xyflow repo before changing path logic.
- Name clashes to watch when editing: `Wpflow.Core.Rect` vs `System.Windows.Rect` (files alias `Rect`/`Path` explicitly) and `System.IO.Path` vs `Shapes.Path`.
